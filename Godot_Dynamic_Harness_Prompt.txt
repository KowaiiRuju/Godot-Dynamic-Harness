GODOT DYNAMIC HARNESS: REVIEW-FIRST PROJECT SETUP

Use this harness to equip my Godot project and IDE agent with the right tools and persistent context. Target Antigravity first; VS Code second.

1. Inspect existing project settings, instructions, tools and test inventory. Preserve current architecture and user customizations. Use existing Graphify queries before codebase investigations when a graph exists; verify relevant findings against source. Never claim an unsupported/missing graph ran.

2. Run the harness checkout's planning command:
   python bootstrap.py plan --project "<game root>" --ide antigravity
   Choose vscode/both if requested. Select the actual --godot executable when discovery is ambiguous.
   If Graphify is missing, propose --graphify install; do not install it yet.
   Propose --smoke only when a generic main-scene test fits the observed startup flow.
   Propose --png-grid for PNG comparison sheets if Pillow is missing; HTML galleries need no extra package. Dependency installation belongs in the reviewed plan.
   Game-specific helpers/tests require an observed need and a reviewed proposal.

3. Present the generated Markdown plan to the user. Explain project findings, exact file/dependency actions, preserved files, conflicts, optional tests and verification limits. Ask what to adjust. DO NOT invoke apply or install tools until the user explicitly approves the exact plan. Regenerate after changing options or resolving conflicts.

4. After approval, run the exact apply command/digest printed in that plan. Inspect returned status, findings and post-apply checks. A digest identifies the plan; it cannot prove user approval. Record failures and incomplete checks rather than declaring the workspace ready.

5. Keep concise persistent files in the project:
   AGENTS.md and selected IDE instructions
   docs/harness/PROJECT.md, TOOLS.md, CHECKPOINT.md
   graphify-out/graph.json and .harness freshness/setup state
   Preserve user text outside managed blocks. Do not store secrets or copy entire chat logs.

6. In each fresh session, read the concise project/tool/checkpoint documents and run:
   python game.py info --json

7. Before each codebase investigation:
   python game.py graph --json
   python game.py graph --refresh --timeout 120 --json    (if missing/stale/untracked)
   python game.py graph --query "<specific file/symbol/question>" --json
   Narrow queries instead of dumping full reports. If Graphify fails, report the reason and obtain/record approval for a source-only fallback. Graph results are navigation hints; source and engine behavior are the evidence.

8. For development, inspect relevant .tscn before attached GDScript. Keep layout/themes/reusable UI components editable in scenes; scripts bind data, connect signals and implement behavior. Prefer typed GDScript, composition and the existing game's patterns. Do not impose a generic architecture or blanket ScrollContainer mouse-filter rule.

9. Use info's real command/argument inventory and follow tiered testing strategies (see docs/TESTING_GUIDE.md):
   - Smoke Testing: Run python game.py test --suite tests/test_harness_smoke.gd --json (or capture --json) after setup or engine switches to ensure the engine boots and autoloads run. Stop if it fails.
   - Sanity Testing: Run focused suite/scene tests (python game.py test --suite <path> --json or capture --scene <path> --json) immediately after surgical edits to verify targeted behavior.
   - Regression Testing: Run full test sweeps (python game.py test --json), batch captures (capture --all-scenes --json), engine checks (validate --engine --json), and syntax scans (syntax --scan . --json) before finishing tasks or committing. Review labeled gallery/contact sheets and manifests; batch failures stay visible.
   Capture preserves the project renderer by default and requires graphics; engine execution is not sandboxed by save-profile isolation. Ephemeral debug captures automatically retain the 5 most recent runs; use python game.py clean --captures --json (or clean --all --json) to purge captures and QA review galleries before committing.

10. After source/config changes, refresh graph and project context. Keep concise decisions, next steps and unverified assumptions outside the checkpoint's managed block. Static scans, engine parsing/loading, screenshots, gameplay and device/release acceptance are separate gates.

Do not bulk-install or delete skill libraries, automatically upgrade Godot, generate comprehensive gameplay suites, or add MCP/live-editor infrastructure without a separately reviewed need. Never claim agent compliance or token savings based only on generated Markdown files.
